# 内容规则与 AI 整理流程

以下为第一版建议约定。实现时将字段映射到内容 schema，业务含义保持一致即可。

## 内容元信息

| 信息 | 要求 | 含义 |
| --- | --- | --- |
| 标题 | 必须 | 读者能够识别主题 |
| 内容类型 | 必须 | 知识笔记、展示说明或工作记录 |
| 发布状态 | 必须 | 草稿、已发布、已归档 |
| 稳定标识或路径 | 必须 | 更新标题时尽量保留已分享链接 |
| 更新时间 | 必须 | 表示材料更新时间，不表示业务已经同步核验 |
| 摘要 | 展示条目必须 | 支持列表浏览与搜索 |
| 项目 | 可选 | 跨项目通用知识可以为空 |
| 来源 | 涉及具体业务事实时填写 | 指定代码、接口定义、ticket、需求或作者材料 |
| 适用版本或阶段 | 阶段说明按需填写 | 让读者判断是否适用于当前工作 |

资料没有提供的信息保持为空或标注未确认，不用模型推断补成事实。

## 发布状态

- **草稿**：不进入发布产物、搜索索引或公共导航。实现时同时检查正文与草稿专属附件；不能只隐藏菜单。
- **已发布**：作者确认可以供读者使用，仍以页面列出的适用范围为准。
- **已归档**：保留访问链接和历史标识，可以继续搜索。不会因为业务代码有改动就自动重写。

普通知识文档与自定义展示可能使用不同构建入口，草稿排除规则需要分别落实，不能假设主题的一个字段对所有入口都生效。

## 内容之间的关系

- 权威接口定义可以保留在现有平台。门户重点补充字段业务含义、调用流程、异常、边界和设计取舍。
- 正文只保留一个来源；栏目、项目汇总和工作总结通过链接引用。
- 独立 HTML 由一个简短展示条目收录，至少保证该条目可被搜索。
- 工作记录引用已有说明或展示，补充作者贡献与结果；没有测量的数据不填写虚构数字。

## AI 整理步骤

1. 读取用户指定范围的代码或材料，确认输出读者与用途。
2. 选择 [API 说明](templates/api-explainer.md)、[开发笔记](templates/development-note.md) 或 [工作记录](templates/work-record.md) 模板。
3. 生成草稿，区分来源支持的事实、解释性推断和待确认事项。
4. 按信息结构放置内容，关联项目、来源与已有页面。
5. 运行实际存在的构建与检查，预览图示、示例和交互。
6. 由作者核对后，按已授权的公司发布流程交付。

目录索引和导航尽量来自内容元信息或明确的配置，避免新增一篇内容就需要重复填写多份同义信息。

定时整理后续沿用这条流程。调度频率、材料来源和自动发布权限尚未确定。
