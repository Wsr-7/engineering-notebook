# 公司环境交接说明

## 当前交付了什么

本仓库交付通用需求、框架研究、UI 方向、开工计划、内容规则和模板。产品优先级与技术路线已经讨论确认。

应用尚未初始化。没有可运行的开发服务器、构建脚本或 CI；这些需要在公司环境内实现。

## 带入公司后的准备

1. 按公司流程建立内部项目仓库，导入本仓库文档。
2. 确认工作副本的远端指向内部仓库，真实内容留在公司环境。
3. 阅读公司工程规范和已有 Pages 配置，核验运行时、包源及发布能力。
4. 使用 [开工计划](kickoff-plan.md) 的首轮范围开始实现。

导入可使用公司允许的克隆、导入或下载方式。本交接仓库不规定公司内部的工具、操作系统或路径。

## 可以交给公司环境 Agent 的开工任务

下面的文字是建议任务，由作者在公司工作区发起：

```text
请在当前公司内部工作区开发 Engineering Notebook（工程手记）的第一版。

先读取 AGENTS.md、docs/kickoff-plan.md、docs/ui-direction.md 和
docs/content-model.md。产品方向与 Astro + Starlight 技术路线已经确认，
不用重新进行广泛选型。

先检查本仓库、公司工程规范、运行时、依赖包源和已有发布配置。
采用实际可用且相互兼容的已发布依赖；如果有明确阻塞，给出具体证据，
并继续不受影响的工作。

完成一个可以预览和静态构建的站点，包含首页、知识库、展示库、
轻量工作记录和本地搜索。复用 Starlight 文档结构，统一导航与样式，
对展示页采用宽幅自定义布局。

用明确标记的虚构内容提供一篇文档、一张含 request/response Schema、
调用步骤和状态变化的交互说明、一份独立 HTML、一条工作记录。
不用索要真实业务案例。

实现新增、更新、草稿排除和归档保留链接的内容流程。
依据模板与实际项目配置完善 Agent 工作约定和 README 使用说明。

按 kickoff-plan.md 中受影响的验收项验证。报告实际运行的命令、
可复现的结果和仍未验证的事项。公司发布目的地和权限明确时，
按用户授权继续发布并检查真实 URL；条件不齐时完成开发与构建，
准确说明剩余发布条件。
```

## 核验实际发布能力

获得内部仓库或平台入口后，检查 Pages URL、子路径、构建执行方式和资源访问。当前没有这些实际环境信息，因此没有预设 GitHub Actions 版本、发布分支或生产地址。

如果公司有现成的约定，优先适配。界面可交互、构建通过与内部站点可访问是三个不同完成状态。

## 后续工作

手动内容整理与发布可用后，再考虑定时汇总、更多交互模板和直接读取任务系统。最终视觉风格可在实际站点中调整，参考图仅用于说明功能。
